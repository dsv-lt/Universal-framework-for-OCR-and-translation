# Архитектура `im_Translator`

**`im_Translator`** — открытый модульный фреймворк для распознавания и перевода вымышленных, зашифрованных и малоресурсных письменностей с изображений. Архитектура спроектирована так, чтобы один и тот же пайплайн работал на разном пользовательском железе (CPU, NVIDIA CUDA, AMD DirectML, Apple Silicon) и легко расширялся через **Языковые пакеты (Language Packs)**.

---

## 1. Общая схема пайплайна

```text
[Входное изображение]
   │
   ▼  Стадия 1. Детекция и выпрямление (ONNX, 1 проход)
   │  • CRAFT (тепловые карты region + affinity) или DBNet++ (prob_map + unclip)
   │  • Группировка фрагментов (устойчивость к перекрытиям) + сортировка (ltr/rtl/ttb)
   │  • Выпрямление перспективы (cv2.getPerspectiveTransform + warpPerspective)
   │
[Выпрямленные кропы строк или блоков]
   │
   ▼  Стадия 2. Распознавание письменности (--lang <pack_id>)
   │  • ONNX OCR (PARSeq / SVTR / TrOCR в ONNX Runtime — лёгкий, работает везде)
   │  • VLM PEFT (Qwen2.5-VL + сменный LoRA-адаптер на каждый язык)
   │  • VLM llama.cpp (мультимодальный GGUF через OpenAI-совместимый llama-server)
   │
[Сырой распознанный текст (Raw)]
   │
   ├─► (Опционально) Стадия 2.5. Промежуточный слой (postprocess.py)
   │   • Выполняется, только если postprocess.enabled: true и включён в UI/CLI
   │   • Контракт: transform(raw_text: str, context: dict) -> dict
   │   • Примеры: шифр Атбаш ([HL] ↔ Basq), декодер чисел, нормализация диакритики
   │
[Текст для перевода (Source или Intermediate)]
   │
   ▼  Стадия 3. Пивот-перевод [Source] → [EN] → [Target]
   │  • GlossaryRAG: поиск совпадений в glossary.json + правила из grammar.md
   │  • Опциональная текстовая Conlang LoRA (для сложных конлангов)
   │  • Любой OpenAI-совместимый API: llama-server, Ollama, LM Studio, vLLM, облако
   │
[Вывод: Raw + Postprocessed + EN + Target]
```

### Почему распознавание и перевод разделены?
1. **Проверяемость:** при прямом шаге `Картинка → EN` модель при смазанном символе склонна додумывать правдоподобные английские слова, и невозможно проверить, что было в оригинале (особенно в именах собственных, заклинаниях и числах).
2. **Опциональный промежуточный слой:** шифрам (`[HL] → Basq`) нужен детерминированный `postprocess.py`, а полноценным конлангам (`Quenya → EN`) он не нужен — у них сразу идёт транскрипция.
3. **Пивот через `EN`:** у компактных открытых LLM лучше всего представлены английский язык и англоязычные грамматики конлангов. Цепочка `Source → EN → Target` повышает качество перевода и сохраняет гибкость выбора переводчика.

## 2. Поддержка 3 классов языков и типов письменностей

Каждый пакет в `packs/<pack_id>/manifest.yaml` указывает свой класс (`language_class`) и свойства письма (`script`):

| Класс | Примеры | Роль OCR | Роль `postprocess.py` | Роль перевода |
| :--- | :--- | :--- | :--- | :--- |
| **`cipher`** | `[HL]` (Mushoku Tensei), Aurebesh, Daedric | Читает глифы в транскрипцию или целевой шифротекст | Симметричный шифр, таблица чисел, нормализация | Базовая LLM переводит расшифрованный естественный язык (`Basq → EN → RU`) |
| **`conlang`** | Квенья, Клингонский, Валирийский, авторские языки | Читает глифы в латинизацию / IPA / каноническую запись | Обычно отключён (либо нормализация орфографии) | **RAG (`glossary.json`) + `grammar.md`** в системном промпте, либо опциональная **Conlang Text LoRA** |
| **`natural`** | Малоресурсные и редкие исторические языки | Читает оригинальную графику | Нормализация пробелов/лакун/сокращений | `glossary.json` + `grammar.md` + соседние строки как контекст |

### Типы письменностей (`script.script_type` и `script.direction`)
- **Направление письма (`direction`):** `ltr` (слева направо), `rtl` (справа налево), `ttb` (сверху вниз). Детектор и рендерер синтетики учитывают направление при сортировке регионов и раскладке символов.
- **Системы письма (`script_type`):** `alphabet`, `abugida`, `abjad`, `syllabary`, `logography`, `cursive`.

## 3. Двойной рендерер для синтетики (`sprites` vs `font`)

Для создания обучающих выборок без обязательного поиска готовых `.ttf`-файлов поддерживаются два рендерера под единым интерфейсом (`script.renderer`):

1. **`sprites` (`glyphs/` + `glyphs_meta.yaml`):**
   - Используется, когда готового шрифта нет (например, вырезанные из скриншотов буквы `[HL]`).
   - Поддерживает **несколько PNG-вариантов** на один символ (`a_1.png`, `a_2.png`) для имитации вариативности почерка.
   - Поддерживает `baseline_offset`, `scale`, `advance_ratio`, а также комбинируемые знаки (`is_combining: true`, `anchor`, `anchor_offset`) для диакритики/огласовок.
2. **`font` (`.ttf` / `.otf`):**
   - Используется для Тенгвара, Ауребеша, клингонского и любых языков с готовым векторным шрифтом.
   - При наличии `libraqm` в Pillow автоматически работают лигатуры, кернинг, диакритика абугид и `rtl`.

Оба режима можно переключать прямо в `manifest.yaml` и в веб-интерфейсе на вкладках **Pack Studio** и **Synth & Train**.

## 4. Детекторы текста: `CRAFT` vs `DBNet++`

На реальных скриншотах текст редко бывает идеально выровненным: он лежит под углом, разбит на несколько записок или частично перекрыт рукой/рамкой. Вместо многократного цикличного вырезания используется **однопроходная детекция** в ONNX с переключением в UI:

- **`CRAFT`** *(рекомендуется по умолчанию для неизвестных шрифтов)*: строит две тепловые карты — **Region Score** (вероятность центра символа) и **Affinity Score** (связь между соседними символами). Не зависит от конкретного алфавита, поэтому хорошо находит даже вымышленные глифы.
- **`DBNet++`**: бинаризует карту вероятности текстовых областей (`prob_map`) и расширяет контуры методом `unclip`. Работает очень быстро и хорошо выделяет плотные блоки и строки.

**Постобработка геометрии (`detection/dewarp.py`):**
- Фрагменты одной строки (например, разорванные перекрытием руки) объединяются по вертикальному перекрытию и углу наклона (`group_and_sort_regions`).
- Все регионы сортируются в естественном порядке чтения (`ltr` / `rtl` / `ttb`).
- Каждый полигон выпрямляется матрицей перспективы (`warpPerspective`) перед подачей в OCR.

## 5. Переносимость и нюансы `llama.cpp` vs `PyTorch` vs `ONNX`

Чтобы проект без боли запускался у других пользователей GitHub:
1. **Ленивый импорт тяжёлых ML-библиотек:** ядро, CLI, Web UI, валидатор пакетов, генератор синтетики и RAG работают только на лёгких зависимостях (`pydantic`, `opencv-python-headless`, `pillow`, `fastapi`, `httpx`).
2. **Три равноправных OCR-бэкенда:**
   - `onnx_ocr`: модели по 30–150 МБ на язык, работают через `onnxruntime` на CPU, CUDA, DirectML и CoreML/MPS без установки PyTorch.
   - `vlm_peft`: одна базовая VLM (например, `Qwen2.5-VL-3B-Instruct`) + лёгкие LoRA-адаптеры (~50–200 МБ на язык). Удобно, если обучены vision-слои (`finetune_vision_layers=True`).
   - `vlm_llamacpp`: вызов внешнего `llama-server` с мультимодальной моделью.
     > **Важно про `llama.cpp`:** текущий `llama.cpp` не умеет динамически подгружать *vision-LoRA* на лету отдельно от `mmproj`. Поэтому при использовании дообученных vision-слоёв в `llama.cpp` LoRA нужно предварительно смерджить и экспортировать в GGUF (`model.gguf` + `mmproj.gguf`), либо использовать `vlm_peft` / `onnx_ocr` для сменных адаптеров.
3. **Хранение в WSL2 + Windows:** в WSL2 Python virtualenv рекомендуется держать на Linux ext4 (`~/.venvs/im_translator`), а тяжёлые модели, датасеты и проект — на отдельном диске (например, `/mnt/d/ai/im_Translator`).

## 6. Структура Языкового пакета (`packs/<pack_id>/`)

```text
packs/<pack_id>/
├── manifest.yaml         # Обязательный паспорт пакета
├── glyphs/               # Если script.renderer == "sprites": PNG-спрайты (RGBA)
├── glyphs_meta.yaml      # Выравнивание и варианты спрайтов
├── font.ttf              # Если script.renderer == "font": векторный шрифт
├── postprocess.py        # Опционально: промежуточный слой transform(raw_text, context)
├── glossary.json         # Опционально: словарь терминов/имён для RAG
├── grammar.md            # Опционально: грамматика и few-shot примеры для системного промпта
└── models/               # Опционально (в .gitignore): обученные локальные веса/адаптеры
```
